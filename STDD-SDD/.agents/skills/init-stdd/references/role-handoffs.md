# 初始化与角色交接

目标描述用于起草首个切片。把用户明确提出的行为保留为事实，把从一句话推测的权限、默认规则、体验或架构写为待确认。已有项目的事实从代码、规格和测试取得，变更目标从用户或已确认的工单取得。

| 角色 | 首次打开 | 草稿应能交给下一角色的内容 |
| --- | --- | --- |
| 产品 | `docs/stdd/project.md`、`changes/<id>/change.md` | 目标用户、成功结果、范围、非目标、要保留的现行行为和未决取舍 |
| 设计 | `changes/<id>/ux-design.md` | 用户流程和可观察状态，有原型时链接，给关键状态关联场景 ID。无界面变更可注明适用范围 |
| 研发 | `changes/<id>/design.md`、`tasks.md` | 入口、依赖、兼容与迁移风险，按能独立验证的结果拆切片 |
| 测试 | `changes/<id>/test-plan.md`、`verification.md` | 主路径、边界、失败和不变行为，注明测试层、用例数据、预期及证据出口 |

让四个角色共用 `changes/<id>/spec.md` 中的 `REQ` 和 `AC`，设计稿、服务设计、任务及测试通过 ID 引用。首份 `spec.md` 处于草稿状态。之后按团队流程评审，同步需求、验收测试和实现，再随交付将已实现的行为落到 `specs/<capability>/spec.md`。

例如，目标明确提出「禁止同一会议室的预约时段重叠」时，可先起草两条场景，同一会议室时间重叠时拒绝，时间不重叠时允许。相邻时段是否重叠、谁能取消以及冲突提示怎么显示，可以记录给负责人决定。研发可先标出并发写入约束，测试可标出从 API 或其他公开入口验证的方式，并记录后续需要跑的并发用例。
