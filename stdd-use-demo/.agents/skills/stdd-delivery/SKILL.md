# 规范与测试驱动交付

1. 从仓库根目录读取 `AGENTS.md`。找出当前变更及其引用的工程约定、规范、契约和测试。如果代码与生效规范冲突，说明具体差异，确认本次应修实现还是修规范。
2. 按用户要求进行规范编写、验收测试、实现或评审。起草规范时标明来源、假设和需保留的行为。对尚待决定的业务行为，列出备选结果和受影响 ID，先推进独立且已明确的工作。
3. 对行为变更，优先在最贴近规则的稳定入口上补测试。在旧实现能够运行的情况下，先确认测试因为预期行为差异而失败。明确场景 ID、测试名和失败断言。
4. 实现已确认的行为，复跑定向测试和仓库规定的完整检查。已评审的预期变更应回到规格评审，跳过的验证应写明范围和原因。
5. 使用 `docs/stdd/templates/verification.md` 记录已确认的规格、受测提交或本地状态、命令和观察结果。仓库有专门评审规则时，审查以目标分支的规则为依据。将已确认的验收预期与候选差异及证据核对，指出缺失的边界、可疑断言或证据版本不符，并标记对应文件和场景 ID。
